Every time inventory, a return, a price, a preference changes — it has to propagate across all four. That sync breaks. Often. At 3 AM. Your agent reasons on four different versions of reality.

The model has no memory by design. Every LLM — Copilot, GPT, Claude — is a next-word predictor trained on frozen data. When the chat ends, everything is gone. There is no "remember Sarah" button inside the model.

The somewhere-else is a mess. Memory has to come from outside the model — and most retailers have four separate systems holding together with duct tape.

This is not a model problem. You can't prompt your way out of it. Bigger context windows won't fix it. It's an architecture problem — and it needs an architecture answer.

Appendix · Anticipated questions

Reference — if asked.

Answers in plain English. Tap any card to see the underlying architecture reasoning.

"We already have Azure OpenAI and Cosmos DB / Aurora. Why another database?"
MySQL-compatible wire protocol — if you're on Aurora, the app doesn't change. Adds native vector + real-time analytics on live data. On Marketplace, burns down the same MACC you're already committing to. Additive to Microsoft's stack, not competitive.
"Our data cannot leave our tenant."
BYOC in Azure — runs inside your Azure VPC. Control plane never touches customer data. PrivateLink only. Your IAM, your keys, your encryption.
"What about Copilot / Copilot Studio?"
Copilot is the language centre — the reasoning layer. This is the memory layer underneath it. They connect via MCP (Model Context Protocol). Complementary, not competing.
"How is this different from pgvector on Aurora?"
Two things. (1) pgvector hits a ceiling around 10M vectors — Manus runs 10M databases on this. (2) pgvector still leaves analytics in a separate warehouse, so your agents reason on stale data. This keeps SQL, vectors, and real-time analytics in one transaction boundary.
"What does migration from Aurora look like?"
Typically a weekend with two engineers. Snapshot, replicate binlog in real-time, 48–72 hours of dual-write validation, DNS cutover. iSoftStone has done it before — Jason can walk through the methodology.
"Pinecone benchmarks better on vector recall."
In isolation, yes. The question isn't raw recall — it's whether running two systems with a sync job between them beats one unified system. The sync lag, the failed deletes, the Right-to-Delete cascade that doesn't reach your vector store — those costs show up in your 3 AM pages, not a benchmark.
"We're evaluating CockroachDB / YugabyteDB / PlanetScale."
MySQL compatibility is the unlock vs. Cockroach's Postgres-first approach. HTAP (real-time analytics on live data) is the unlock vs. all of them. Vector search native is the unlock vs. PlanetScale. Happy to do a head-to-head on a specific workload.
"What's the compliance story — CCPA, EU exposure?"
One ACID audit log covers every agent decision. Right-to-Delete cascades through the relational layer and the vector layer in one transaction — they're the same engine. That's something a Frankenstack fundamentally can't give you.
