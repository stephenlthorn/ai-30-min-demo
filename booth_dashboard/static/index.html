Appendix · Anticipated questions

Reference — if asked.

Answers in plain English. Tap any card to see the underlying architecture reasoning.

"We already have Postgres / MySQL / Aurora. Why another database?"
MySQL-compatible wire protocol — if you're on Aurora or MySQL, the app doesn't change. Adds native vector search + real-time analytics on live data in one transaction boundary. Replaces three or four systems with one.
"Our data cannot leave our tenant."
BYOC — runs inside your own cloud account. Control plane never touches customer data. Your IAM, your keys, your encryption. PrivateLink only.
"What about Copilot / Bedrock agents / Vertex agents?"
Those are the reasoning layer — language centres. This is the memory layer underneath them. They connect via MCP (Model Context Protocol). Complementary, not competing — works with any agent framework.
"How is this different from pgvector on Postgres?"
Two things. (1) pgvector hits a practical ceiling around 10M vectors — Manus runs 10M+ databases on this. (2) pgvector still leaves analytics in a separate warehouse, so your agents reason on stale data. TiDB keeps SQL, vectors, full-text, and real-time analytics in one transaction boundary.
"What does migration from Aurora / MySQL look like?"
Typically a weekend with two engineers. Snapshot, replicate binlog in real-time, 48–72 hours of dual-write validation, DNS cutover. MySQL-compatible means your apps don't change.
"Pinecone benchmarks better on vector recall."
In isolation, yes. The real question isn't raw recall — it's whether running two systems with a sync job between them beats one unified system. The sync lag, the failed deletes, the Right-to-Delete cascade that doesn't reach your vector store — those costs show up in your 3 AM pages, not a benchmark.
"We're evaluating CockroachDB / YugabyteDB / PlanetScale."
MySQL compatibility is the unlock vs. Cockroach's Postgres-first approach. HTAP (real-time analytics on live data) is the unlock vs. all of them. Native vector + full-text is the unlock vs. PlanetScale. Happy to do a head-to-head on a specific workload.
"What's the compliance story — CCPA, GDPR, EU exposure?"
One ACID audit log covers every agent decision. Right-to-Delete cascades through the relational layer and the vector layer in one transaction — they're the same engine. That's something a Frankenstack fundamentally can't give you.
"How does the memory stay accurate over time? Doesn't it get stale or contradictory?"
Memory has five maintenance duties — all running inside a single TiDB cluster, no external schedulers:
Write control — Only confirmed outcomes persist. Working reasoning stays ephemeral.
Deduplication — Cosine similarity < 0.15 merges with existing memory. One strong memory, not ten weak ones.
Reconciliation — New evidence auto-supersedes contradicted conclusions. Stale facts are linked, not lost.
Confidence decay — 5% monthly decay without reinforcement. Below 0.30 = auto-deprecated.
Compaction — Weekly re-clustering merges drifted memories. Evidence counts consolidated.
